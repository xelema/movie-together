● Ce que j'ai trouvé

  Ton image n'est pas arrivée dans le message (aucune pièce jointe côté outil).
  J'ai reproduit le problème avec data/color-diagnostic/original.mp4 et mesuré
  les quatre navigateurs.

  Cause racine, mesurée, pas supposée.
  Sur écran SDR, Chromium comprime toute la plage PQ vers la luminance crête que
  le fichier déclare.
  Ton film annonce 1 000 cd/m² (SEI mastering display) et MaxCLL 1033, donc
  Chromium écrase les tons moyens.
  Firefox ignore complètement cette valeur et applique une courbe fixe. D'où
  l'écart.

  Mire PQ en paliers, valeur sRGB lue dans un canvas :

  ┌──────────────┬───────────┬─────────┬──────────┐
  │ Code 10 bits │ Luminance │ Firefox │ Chromium │
  ├──────────────┼───────────┼─────────┼──────────┤
  │ 448          │ 49 cd/m²  │ 130     │ 95       │
  ├──────────────┼───────────┼─────────┼──────────┤
  │ 512          │ 103 cd/m² │ 170     │ 128      │

  └──────────────┴───────────┴─────────┴──────────┘

  Deux découvertes qui expliquent pourquoi l'approche évidente échoue :

  - Chromium ignore les boîtes conteneur mdcv / clli pour HEVC. Testé : aucun
    effet, même après avoir
    supprimé les SEI. Il les lit pour VP9 et AV1.
  - Il lit la crête dans les SEI du flux. SEI à 250 → plus clair, SEI à 4 000 →
    plus sombre. Vérifié.

  Ce que j'ai fait

  src/media.js réécrit la crête annoncée à 250 cd/m² pendant la préparation :
  SEI 137 et 144 pour HEVC, boîtes mdcv / clli pour les autres codecs.
  250 est la valeur mesurée qui colle le mieux à la courbe de Firefox.

  - Aucun encodage. 7 octets changent par segment, avant la première tranche.
  - framemd5 source contre version préparée : identiques. Le test le vérifie.
  - RPU Dolby Vision (NAL 62) intact.

  vidéo sur cette machine.

  Ce que j'ai éliminé :
